1 Contracted definitions🔗

 (require torch/private/contract) package: base

Two forms that attach a contract to a definition at its definition site, so the contract sits next to the code it describes rather than in a contract-out block at the exporting facade. Both are allowed only at module level, because each expands to a provide.

syntax

(define/contract-out id contract-expr expr)

(define/contract-out header contract-expr body ...+)
 
  contract-expr : contract?
Defines id (or the name at the base of header, as define would) and exports it with contract-expr via contract-out. Inside the defining module the binding is uncontracted, exactly as with contract-out: only callers that import it cross the contract boundary, and blame falls on them.

contract-expr may refer to bindings defined later in the module.

(define/contract-out (safe-div a b)
  (-> number? (not/c zero?) number?)
  (/ a b))

The first form also promotes a binding defined elsewhere under a contracted name, which is how an uncontracted generated or FFI-level operation reaches the public surface:

(define/contract-out narrow
  (-> tensor? exact-integer? exact-integer? exact-positive-integer? tensor?)
  g:narrow)

syntax

(define/checked-out id contract-expr expr)

(define/checked-out header contract-expr body ...+)
 
  contract-expr : contract?
Like define/contract-out, but exports the definition plainly and puts the contracted name in a checked submodule:

(define name expr)
(provide name)
(module+ checked (provide (contract-out [name contract-expr])))

A module that requires the defining module reaches the uncontracted definition. A module that wants the contract requires (submod "the-module.rkt" checked) instead. This is the form for a name the library itself calls: the public facade opts in to the contract, while the library’s own calls to the same name pay nothing.

module+ accumulates across every use in a file and sees the enclosing module’s bindings, so contract-expr may name the module’s imports as freely as in define/contract-out.

Which form to use is decided by one question: does another module in the library import this name? If so, define/checked-out; if not, define/contract-out.

2 Transpose shorthand🔗

 (require torch) package: base

procedure

(T x) → tensor?

  x : tensor?
Returns a view with all dimensions in reverse order, matching Python’s x.T. A matrix of shape [M, N] becomes [N, M]; a tensor of shape [B, H, S, D] becomes [D, S, H, B]. Scalars and vectors retain their shapes. Storage is shared with x, and gradients propagate through the view.

(T (tensor '((1 2 3) (4 5 6))))
(~> x T)
(@ x (T weight))

For batched attention keys, use (transpose keys -2 -1) to swap only the last two dimensions. That operation corresponds to Python’s keys.mT, whereas T reverses every axis.

PyTorch deprecates .T for tensors whose rank is not two. This shorthand supports all ranks without emitting a deprecation warning.

 (require torch) package: base

Python’s len, shadowing racket/base’s length the way + is shadowed: a list, vector, string or hash answers what it always did, a tensor answers its first dimension, and a dataset or loader answers its number of items or batches.

(length '(1 2 3))
(length (zeros 4 2))
(length (dataloader ds #:batch-size 64))

A rank-zero tensor has no length, as len of a 0-d tensor raises.

  v : any/c
Recognises anything length accepts.

The generic behind length, with that one method. A structure implements it with #:methods; define-dataset does so for every dataset.

4 Devices and dtypes🔗

 (require torch) package: base

procedure

(to x target) → (or/c tensor? to-able?)

  x : (or/c tensor? to-able?)
  target : (or/c device/c dtype/c)
(to x target dtype) → (or/c tensor? to-able?)
  x : (or/c tensor? to-able?)
  target : device/c
  dtype : dtype/c
PyTorch’s .to: moves x to a device, casts it to a dtype, or both in one native hop. A device target is any device/c form, 'cuda, (device 'cuda 1), or a device? value; a dtype target is one of 'float32, 'float64, 'int64, 'bool, 'uint8. As in Python, the dtype may follow a device target but a dtype target stands alone.

(to x (device 'cuda))
(to x 'float64)
(to x 'cuda 'float32)
(~> x (to 'cuda))

For a tensor, the result is a new tensor and x is untouched, except that when nothing would change the result is x itself, as x.to("cpu") is x in PyTorch. The identity matters for the memory ledger: a second wrapper over aliased storage would be charged twice (see native-memory-use).

For a layer, or any value with prop:to, the move happens in place and returns x. Every layer from torch/nn is to-able?: each of its parameters and buffers is rebound to the moved storage under the same object, so references held by the caller, by optimizers, and by the layer tree all stay valid; an accumulated gradient moves along, and the parameter stays a requires-grad leaf. Plain tensor fields are not moved, just as PyTorch leaves plain tensor attributes where they are; register such a tensor with Buffer to have it follow the layer. A layer’s dtype target must be floating-point, 'float32 or 'float64, as nn.Module.to only accepts floating-point or complex dtypes, and as there it reaches only the floating-point parameters and buffers: an 'int64 counter or a 'bool mask registered with Buffer keeps its dtype and changes device alone.

Optimizer state follows: adam creates its moments on the parameter’s device and dtype at the first step!, and a moment created before a later move is brought to the parameter at the next step, so a model may be moved at any point of training. One rule carries over from PyTorch: a move that fails part-way, for example on a CUDA out-of-memory error, leaves the layer with some parameters moved and some not.

(define model (Linear 784 10))
(load-state! model "mnist.safetensors")
(to model (device 'cuda))

to-device and to-dtype are the single-axis primitives underneath to; both share its identity behaviour.

value

device/c : contract?

A device designator: a device? value, one of 'cpu, 'cuda, 'mps, or (list 'cuda index).

value

dtype/c : contract?

One of 'float32, 'float64, 'int64, 'bool.

value

prop:to : struct-type-property?

A structure type property whose value is a procedure of three arguments, the instance, a device? or #f, and a dtype symbol or #f, at least one of which is supplied. It is called by to to move the instance and must return the moved value. Layers receive it through gen:layer; a container of tensors outside the layer system can implement it directly.

procedure

(to-able? v) → boolean?

  v : any/c
Recognises values carrying prop:to.

procedure

(to-device t dev) → tensor?

  t : tensor?
  dev : device/c
Equivalent to (to t dev).

procedure

(to-dtype t dtype) → tensor?

  t : tensor?
  dtype : dtype/c
Equivalent to (to t dtype).

4.1 Placement at construction🔗

procedure

(zeros dim    
  ...    
  #:device device    
  #:dtype dtype    
  [#:requires-grad? requires-grad?]) → tensor?
  dim : exact-nonnegative-integer?
  device : device/c
  dtype : dtype/c
  requires-grad? : boolean? = #f
(zeros dims    
  #:device device    
  #:dtype dtype    
  [#:requires-grad? requires-grad?]) → tensor?
  dims : (listof exact-nonnegative-integer?)
  device : device/c
  dtype : dtype/c
  requires-grad? : boolean? = #f
A tensor of zeros, with the dims as rest arguments or as one list, as torch.zeros(2, 3) and torch.zeros((2, 3)). The device and dtype default to the process default device and 'float32; when given they are chosen at native construction, so a tensor never takes a hop through another device on its way to where it will live. With #:requires-grad? the result is marked as a leaf after construction, which an integer dtype refuses as PyTorch does. ones, full, randn, and rand take the same arguments; the two random constructors accept only 'float32 or 'float64 and draw from the chosen device’s generator.

arange and eye take the same three keywords after their positional arguments. arange stays 'float32 by default, as before; (arange n #:dtype 'int64) is the index vector torch.arange(n) produces.

procedure

(zeros-like t    
  #:device device    
  #:dtype dtype    
  [#:requires-grad? requires-grad?]) → tensor?
  t : tensor?
  device : device/c
  dtype : dtype/c
  requires-grad? : boolean? = #f
Zeros with t’s shape, device, and dtype unless overridden, as torch.zeros_like. ones-like, full-like (which takes the fill value after t), randn-like, and rand-like are the same for their constructors. Optimizer state is the typical use: a moment created by zeros-like lives where its parameter does, however the parameter got there.

4.2 Native memory🔗

Every tensor’s native storage is released by a finalizer when Racket’s collector finds its handle unreachable. The ledger charges each allocation to the collector as phantom bytes, so ordinary programs never call the collector by hand. A training loop is the exception. Handles that survive the collections of a step wait for a full one, and when Racket happens to run a full collection in the middle of a forward pass, that pass’s intermediates are promoted to the oldest generation, where Racket will not look again until its memory use has doubled: a whole step’s storage stays behind and the next step runs out. The ledger therefore collects by itself, in two places. The first is the trough of a training step: backward! has just released the graph, the forward pass’s intermediates are dead and little is live, so a full collection there reclaims the most and promotes the least. When the ledger has grown by more than a margin (between 256 MiB and 1 GiB) over its size after the previous such collection, backward! runs one before it returns and yields until the finalizers have drained; the collections are spaced so that they take about 5% of wall-clock time. A program whose residue never reaches the margin never sees one. A sampling or evaluation loop never calls backward!; its trough is the return of an outermost layer call while gradients are off (see with-no-grad), where nothing of the forward pass outlives its result. That garbage is young, so a minor collection is tried first and a full one takes only what survives, the two sharing the same 5%. With gradients on the same moment is the peak of a step, and nothing is done there. The second place is a backstop for code with neither trough: when a device’s live bytes pass its high-water mark, the next allocation runs the same drained collection. Live bytes are the larger of the ledger’s total and the CUDA caching allocator’s own allocated figure, sampled as allocation proceeds, because storage that only the autograd graph still holds is invisible to the ledger. The mark is native-memory-fraction of the device’s capacity, from cuda-memory-info on CUDA and mps-memory-info on MPS, or native-memory-limit when set. A collection is never run within an eighth of the mark of the previous one, measured in bytes allocated, and when a collection reclaims under 5% of the mark that spacing doubles, so a working set that legitimately sits above the mark is not collected on every step.

Every knob above is a parameter, so a training script can tune the whole policy for its own machine by wrapping its loop once:

(parameterize ([native-memory-fraction 9/10]
               [native-collect-budget 1/50]
               [native-collect-margin (* 2 1024 1024 1024)])
  (train!))

Raising the fraction and the margin and lowering the budget all trade peak memory for throughput. The defaults are deliberately cautious, and were measured on one model on one card, so a machine with more memory than compute has room to relax them.

procedure

(native-memory-use)

 → (listof (cons/c device? exact-nonnegative-integer?))
Live native bytes per device as the ledger sees them: every handle not yet released, at the byte count of its own extent. Views charge their full extent, so shared storage is counted once per handle, and libtorch’s own internal allocations are absent.

parameter

(native-memory-limit) → (or/c #f exact-positive-integer?)

(native-memory-limit limit) → void?
  limit : (or/c #f exact-positive-integer?)
The high-water mark in bytes for every device, overriding the capacity- derived mark. #f, the default, defers to the device’s capacity; on a device whose capacity is unknown, such as the CPU, the default leaves pressure collection off.

parameter

(native-memory-fraction) → (and/c real? positive? (<=/c 1))

(native-memory-fraction fraction) → void?
  fraction : (and/c real? positive? (<=/c 1))
The share of a device’s capacity the backstop treats as its high-water mark, 4/5 by default. Read at every check, so it may be parameterized at any point in a run. Ignored where native-memory-limit is set or the capacity is unknown.

parameter

(native-collect-margin) → (or/c #f exact-positive-integer?)

(native-collect-margin margin) → void?
  margin : (or/c #f exact-positive-integer?)
How far in bytes the ledger may grow past its size after the previous collection at a trough before another is due. #f, the default, tracks that size itself, kept between 256 MiB and 1 GiB. A larger margin collects less often and holds more.

parameter

(native-collect-budget) → (and/c real? positive?)

(native-collect-budget budget) → void?
  budget : (and/c real? positive?)
The share of wall-clock time collections at a trough may take, 1/20 by default. After one costing t the next waits t divided by the budget, so a smaller budget spaces them further apart and a larger one collects more eagerly.

procedure

(mps-memory-info)

 → 
(listof (cons/c (or/c 'allocated 'driver-allocated 'recommended-max)
                exact-nonnegative-integer?))
The MPS allocator’s own gauges: bytes handed out, bytes taken from the driver, and the working-set maximum Metal recommends staying under, which is what the backstop’s mark is taken from on that device. All three are zero when the backend is absent, rather than raising.

procedure

(cuda-memory-info [dev])

 → (listof (cons/c (or/c 'free 'total) exact-nonnegative-integer?))
  dev : device/c = (cuda-device)
The driver’s free and total bytes for a CUDA device, as torch.cuda.mem_get_info. Free counts other processes and this process’s reserved-but-unallocated cache; total is the capacity the high-water mark is taken from. Raises when CUDA is absent.

procedure

(cuda-memory-stats [dev])

 → 
(listof (cons/c (or/c 'allocated 'reserved 'peak-allocated)
                exact-nonnegative-integer?))
  dev : device/c = (cuda-device)
The CUDA caching allocator’s own numbers for this process: bytes allocated now, bytes reserved from the driver, and the peak allocated.

procedure

(cuda-reset-peak-stats! [dev]) → void?

  dev : device/c = (cuda-device)
Resets the allocator’s peak counters, as torch.cuda.reset_peak_memory_stats, so the next 'peak-allocated covers only what follows.

procedure

(cuda-allocator-settings! settings) → void?

  settings : string?
Applies a PYTORCH_CUDA_ALLOC_CONF string to the caching allocator, as torch.cuda.memory._set_allocator_settings: "expandable_segments:True" lets segments grow in place instead of fragmenting, "garbage_collection_threshold:0.8" has the allocator return cached blocks once reserved memory passes that fraction of capacity. Options that shape segments affect only segments created afterwards, so call it before the first CUDA allocation. Does nothing in a build without CUDA; raises on a string the allocator’s parser rejects.

procedure

(reclaim-native-memory!) → void?

Collects and drains repeatedly, up to four rounds, while the ledger keeps shrinking, then returns the CUDA and MPS caches to their drivers. For epoch boundaries and script exits; a training loop no longer needs it.

procedure

(finalizer-diagnostics) → (listof (cons/c symbol? any/c))

An association list with the finalizer run and failure counts, the captured failure messages, the number of ledger entries, and the collections the ledger has made: 'trough-collections and 'trough-minors, the full and minor collections at a trough, 'pressure-collections from the high-water backstop, and under 'pressure-reclaimed the bytes all of them released.

4.3 Unsafe🔗

 (require (submod torch/foreign unsafe))

procedure

(to! t target) → tensor?

  t : tensor?
  target : (or/c device/c dtype/c)
(to! t target dtype) → tensor?
  t : tensor?
  target : device/c
  dtype : dtype/c
The in-place primitive behind a layer move: rebinds t’s storage to the moved copy and returns t. Every reference to t observes the change, which is why it lives in the unsafe submodule; a view or detached copy made earlier is a separate tensor and keeps the old storage, device, and dtype. The tensor’s ledger entry is re-accounted under the same handle, so native-memory-use reports the new device and byte count; the old storage is released by libtorch at once when nothing else references it.

5 Datasets and loaders🔗

 (require torch/data/loader) package: base

The data pipeline is PyTorch’s, without the class hierarchy: a dataset answers a length and an item per index, a loader cuts a sequence of indices into batches, and a collate turns a batch of items into the tensors a training step takes. One traversal of a loader is one epoch.

(define loader
  (dataloader (tensor-dataset xs ys)
              #:batch-size 64 #:shuffle? #t
              #:generator (make-generator 0)))
(for* ([epoch (in-range 3)]
       [(xb yb) (in-dataloader loader)])
  (train-step! xb yb))

5.1 Datasets🔗

syntax

(define-dataset name (field ...) clause ...)

 
field = id
  | [id default-expr]
  | keyword id
  | keyword [id default-expr]
     
clause = #:init (formal ...) init-body ...
  | #:init (formal ... #:rest rest-id) init-body ...
  | #:init (formal ... . rest-id) init-body ...
  | #:length length-expr
  | #:ref (index-id) body ...+
  | #:batch (indices-id collate-id) body ...+
  | #:device device-expr
  | #:contract contract-expr
  | #:predicate id
     
formal = id
  | [id default-expr]
  | keyword id
  | keyword [id default-expr]
 
  contract-expr : contract?
Defines a map-style dataset: a constructor name, a predicate name?, and a structure with one slot per field that implements gen:dataset. The clauses are the methods of a Dataset subclass, with every field in scope: #:init is __init__, #:length is __len__, and #:ref is __getitem__, returning the item at index-id as one value per field. Both are required.

(define-dataset squares (n)
  #:init (n)
  #:length n
  #:ref (i) (values (full (* i i) 2) (tensor i)))

#:init’s formals are the constructor’s arguments, in the grammar of define. Every field starts as #f, or as the argument of the same name when a formal shares it, and init-body assigns fields with set!. Without #:init, the fields are themselves the constructor formals.

#:batch replaces the default batch, which fetches each item with #:ref and hands the list of items to collate-id; use it when a whole batch is one native op, as tensor-dataset does. indices-id is an indices/c, a list or an int64 tensor; indices->list reads either. #:device answers dataset-device, #f by default; it needs #:batch, because a loader then hands #:batch an index tensor resident on that device, which the default batch could only read back with a copy per batch.

#:contract provides the constructor under contract-expr and the predicate under its lowercase name, or the #:predicate one, as define-layer does; without it nothing is exported.

value

gen:dataset : any/c

The generic interface a define-dataset structure implements, with methods dataset-length, dataset-ref, dataset-batch, and dataset-device. A structure written by hand implementing the first two gets the other two by default.

procedure

(indices->list indices)

 → (non-empty-listof exact-nonnegative-integer?)
  indices : indices/c
The indices of a batch as a list, whether a loader handed them over as a list or as an int64 tensor.

value

indices/c : contract?

A non-empty list of natural numbers, or a non-empty rank-one int64 tensor. The tensor’s elements are not read: a loader cuts them from a permutation, possibly on a device, and reading them back would wait on it every batch.

value

collate/c : contract?

A procedure from a non-empty list of items, each a list of fields, to the batch’s values.

procedure

(dataset-device ds) → (or/c device? #f)

  ds : dataset?
Where the dataset’s batches live, or #f when it has no single device. A loader moves each epoch’s permutation there once, so no batch waits on a host-to-device copy. The default is #f; a tensor-dataset answers its first tensor’s device.

procedure

(dataset? v) → boolean?

  v : any/c
Recognises values implementing gen:dataset.

procedure

(dataset-length ds) → exact-nonnegative-integer?

  ds : dataset?
The number of items; length answers the same for a dataset written with define-dataset.

procedure

(dataset-ref ds i) → any

  ds : dataset?
  i : exact-nonnegative-integer?
The item at i, below the length, as one value per field, as dataset[i] in PyTorch returns a tuple.

procedure

(dataset-batch ds indices collate) → any

  ds : dataset?
  indices : indices/c
  collate : collate/c
The batch at indices, as values. indices is a non-empty list of natural numbers below the length, or a non-empty rank-one int64 tensor when a loader cuts it from a permutation.

procedure

(tensor-dataset t more ...) → tensor-dataset?

  t : tensor?
  more : tensor?
A dataset over one or more tensors of rank at least one sharing their first dimension and their device, as TensorDataset, written with define-dataset: item i is (select t 0 i) per tensor. Anything else is a contract violation blamed on the caller. With default-collate, its batches never go through items: a contiguous ascending run of indices is a narrow of each tensor, and any other run is one index-select with the indices on the tensor’s device. Keep the tensors on the training device and a batch costs no host copy. A custom collate sees the items, as collate_fn does.

procedure

(tensor-dataset? v) → boolean?

  v : any/c
Recognises the result of tensor-dataset.

procedure

(default-collate items) → any

  items : (non-empty-listof (non-empty-listof tensor?))
default_collate for tensor fields: one stack per field, as values. Every item must carry the same fields, each of one shape on one device.

procedure

(default-collate? v) → boolean?

  v : any/c
Recognises default-collate however it arrived, through any number of contract boundaries. A #:batch body that computes the default batch natively asks this before taking its fast path, and hands the items to any other collate.

5.2 Loaders🔗

procedure

(dataloader ds    
  [#:batch-size batch-size

  #:collate collate    
  #:generator generator]) → dataloader?

A loader over ds, as DataLoader(ds, batch_size, shuffle, drop_last, collate_fn, generator) with num_workers=0: batches are built on the calling thread when they are asked for. A shuffled loader needs a non-empty dataset within size/c, as RandomSampler and randperm do; an empty one may still be traversed in order. Every traversal draws what one DataLoader iterator draws, in its order, from generator or else the global stream: one draw-seed when the traversal starts, shuffled or not; with #:shuffle? the permutation when the first batch is asked for, and once it is used up the trailing permutation its sampler discards, before a final partial batch or else when the traversal is exhausted. A traversal abandoned early leaves the stream where PyTorch’s would. The stream continues across traversals, so (make-generator s) here and torch.Generator().manual_seed(s) there yield the same batch order epoch after epoch. Without a generator the draws come from the global stream the way RandomSampler makes them, seeding a fresh generator per epoch. Without #:shuffle? the batches are the items in order, and a batch size equal to the length yields the dataset’s own tensors.

7 Layers🔗

 (require torch/nn) package: base

syntax

(define-layer name (field ...) clause ... #:forward (input ...) body ...+)

 
field = id
  | [id default-expr]
  | keyword id
  | keyword [id default-expr]
     
clause = #:init (formal ...) init-body ...
  | #:init (formal ... #:rest rest-id) init-body ...
  | #:init (formal ... . rest-id) init-body ...
  | #:reflection-name expr
  | #:contract contract-expr
  | #:predicate id
     
formal = id
  | [id default-expr]
  | keyword id
  | keyword [id default-expr]
     
input = id
  | [id : input-contract-expr]
 
  contract-expr : contract?
  input-contract-expr : contract?
Defines a layer: a constructor name, a predicate name?, and a struct with one slot per field. An instance is a layer? and applies as a procedure, running body with every field in scope. A call with other than one argument per input raises exn:fail:contract:arity under name, whether made directly, through forward, or through layer-forward.

An input written [id : contract-expr] states what the layer accepts there, and a call that does not satisfy it is a contract violation naming the layer and the contract rather than an error raised from inside the body: a shape the layer cannot take belongs in the signature, not in an unless guard. The check is built once, where the layer is defined, so it costs one flat check per call; the party blamed is the label caller, since a layer’s forward has no module boundary of its own to name the caller by. A bare id accepts anything, as before.

(define-layer BatchNorm2d (weight bias)
  #:forward ([x : image-batch/c])
  (batch-norm x #:weight weight #:bias bias))

#:init is the constructor body, the analogue of __init__. Its formals are the constructor’s arguments, in the grammar of define; the rest argument is spelled #:rest rest-id or as define’s dotted tail. Every field starts as #f, or as the argument of the same name when a formal shares it, and init-body assigns fields with set!. With #:init, a field is a bare identifier. Without it, the fields are themselves the constructor formals, so a stateless layer needs no body. A field name is one state-dict segment and may not contain a dot.

Every layer starts in the 'train mode, and train!, eval! and set-mode! set a layer’s own mode and recurse into its children. body reads the instance’s mode with with-mode. The mode is not a field: it is neither a parameter nor a buffer, and it is not written to the state dict. Other per-instance state that is not a tensor belongs in a plain field holding a box; state that is a tensor belongs in a Buffer updated in place.

(define-layer Dropout (p)
  #:contract (->* [] [#:p (and/c (>=/c 0) (</c 1))] dropout?)
  #:init (#:p [p 0.5])
  #:forward (x)
  (with-mode (dropout x p (training? mode))))

What a field holds when init-body finishes decides what it is:

  • a Parameter? is a parameter: returned by parameters, named by named-parameters, stepped by an optimizer and written to the state dict;

  • a Buffer? is a buffer: returned by buffers, named by named-buffers, written to the state dict after the parameters, but not trained;

  • a layer? is a child: parameters, named-parameters, buffers, train! and eval! recurse into it, and its parameters are named under the field, as in "fc1.weight";

  • a Children? value, from children-by-index or children-by-key, splices its entries in as children under their own names, and the field name is dropped, as add_module in a loop would;

  • #f is a declared but absent slot, skipped by all of the above, as register_parameter(name, None) is;

  • anything else is a plain field, visible to #:forward and otherwise ignored.

parameters lists a layer’s own parameters first and then each child’s, each group in field declaration order. A parameter or child reachable by more than one path, as when two fields hold the same layer, is listed once, under the first path, so an optimizer steps it once; the state dict keeps every path, as PyTorch’s does, so a tied model loads into an untied one. init-body runs sequentially, so the order in which parameters draw from the RNG is the order of the assignments.

#:contract exports the layer. It provides name under contract-expr and the predicate under a lowercase name, both via contract-out, so a violation blames the calling module. The predicate’s export name inserts a hyphen before each uppercase letter that follows a lowercase letter or a digit, then downcases: Linear exports linear?, Conv2d exports conv2d?, MaxPool2d exports max-pool2d?. #:predicate names the exported predicate instead. Both names are bound in the defining module, so contract-expr may use the lowercase one as its range. Like define/contract-out, the clause is allowed only at module level.

(define-layer Conv2d (kernel-size stride padding weight bias)
  #:contract (->* [exact-positive-integer? exact-positive-integer? pos-size/c]
                  [#:stride pos-size/c #:padding nonneg-size/c]
                  conv2d?)
  #:init (in-channels out-channels kernel-size
          #:stride [stride 1]
          #:padding [padding 0])
  (set! kernel-size (->2d kernel-size))
  (set! stride (->2d stride))
  (set! padding (->2d padding))
  (define shape
    (list out-channels in-channels (car kernel-size) (cadr kernel-size)))
  (set! weight (Parameter (kaiming-uniform shape)))
  (set! bias (Parameter (uniform-init (list out-channels) -0.1 0.1)))
  #:forward (x)
  (conv2d x weight #:bias bias #:stride stride #:padding padding))

A container is a layer whose children arrive as a named collection rather than one per field. It builds them with children-by-index or children-by-key and assigns the result to a field; the entries register directly on the container, so Sequential’s parameters are "0.weight" and so on. A step may be a plain procedure such as relu, so a model can mix layers with the functional interface:

(define-layer Sequential (steps)
  #:contract (->* [] #:rest (or/c (list/c (listof step/c)) (listof step/c))
                  sequential?)
  #:init (#:rest ms)
  (set! steps (children-by-index (if (and (pair? ms) (list? (car ms)))
                                     (car ms)
                                     ms)))
  #:forward (x)
  (for/fold ([acc x]) ([m (in-layers steps)])
    (layer-forward m acc)))

An invariant that relates two arguments is a ->i precondition rather than a guard in the body:

(define-layer SelfAttention (n-embd n-head wq wk wv wo)
  #:contract (->i ([n-embd exact-positive-integer?]
                   [n-head exact-positive-integer?])
                  #:pre (n-embd n-head) (zero? (remainder n-embd n-head))
                  [_ self-attention?])
  #:init (n-embd n-head)
  ...)

Without #:contract nothing is exported; a layer local to a model or a test needs no contract boundary.

Wraps proc as a callable layer. Calls through the layer itself, forward, or layer-forward pass positional arguments to proc and preserve its return values and exceptions. Keyword arguments to the wrapped procedure are not supported.

The optional association lists register captured parameters, buffers, and child layers. Names must be unique across all three lists and must not contain dots. Parameters precede children’s parameters in traversal order; shared values are deduplicated by identity. Training and evaluation recurse through registered children, as for define-layer.

Captures are not discovered automatically. In contrast to OCaml’s Layer.of_fn, whose parameters belong to a separate variable store, this wrapper owns its registered tree. Rebinding a captured variable does not change that registration. The wrapper has a training mode of its own that train! and eval! set, but proc cannot read it, so a mode-dependent step belongs in a registered child such as Dropout.

                    (cons "drop" drop))))
(eval! block)

(Sequential steps) → sequential?
  steps : (listof step/c)
A layer that applies each step to the previous step’s result. The steps are its children, named by index, so its parameters are "0.weight" and so on. The steps are given either as arguments or as one list, so a model may build them with for/list.

Recognizes the result of Sequential.

procedure

(in-layers v) → sequence?

  v : (or/c Children? layer?)
A sequence of the children of v, in order, for use in for forms: the entries of a Children? value, or the registered children of a layer. Unlike children, a layer listed more than once is yielded each time, so a tied block in a Sequential applies as many times as it is listed.

procedure

(children m) → (listof layer?)

The direct children of m, in registration order, each listed once however many fields hold it. A LayerList counts as one child; its own children are reached through it.

procedure

(set-mode! m mode) → layer?

  m : layer?
  mode : mode/c
Sets the mode of m and of every layer reachable through its children, and returns m.

Every layer satisfies to-able?: gen:layer derives prop:to, so (to m 'cuda) moves each of (parameters m) and (buffers m) in place, keeps every parameter object and its gradient, and returns m. A hand-written gen:layer implementation gets this for whatever its layer-parameters and layer-buffers report. See to for the rules on optimizer state and plain fields.

procedure

(train! m) → layer?

  m : layer?
(set-mode! m 'train).

procedure

(eval! m) → layer?

  m : layer?

procedure

(layer-mode m) → mode/c

  m : layer?
The mode of m itself. A layer’s mode is its own: eval! on a child does not change its parent’s answer. A hand-written gen:layer implementation that defines no mode methods is stateless and reports 'train.

procedure

(layer-training? m) → boolean?

  m : layer?
(training? (layer-mode m)).

procedure

(layer-set-mode! m mode) → void?

  m : layer?
  mode : mode/c
The gen:layer method behind set-mode!: sets m’s own mode and recurses into its children. A hand-written layer that keeps a mode of its own defines this method and layer-mode; call-with-mode restores such a layer through them. A layer that defines neither is stateless.

procedure

(call-with-mode m mode thunk) → any

  m : layer?
  mode : mode/c
  thunk : (-> any)
Records the mode of every layer reachable from m, sets them all to mode, calls thunk, and restores each layer’s own recorded mode, whether thunk returns or raises. A tree whose layers were in mixed modes comes back exactly as it was.

procedure

(call-with-eval-mode m thunk) → any

  m : layer?
  thunk : (-> any)
(call-with-mode m 'eval thunk).

syntax

(in-mode m mode body ...+)

(call-with-mode m mode (lambda () body ...)).

syntax

(in-eval-mode m body ...+)

(call-with-mode m 'eval (lambda () body ...)).

procedure

(ema model average [#:decay decay]) → ema?

  model : layer?
  average : layer?
  decay : (real-in 0 1) = 0.9999
An exponential moving average of model’s parameters, kept in average: a second layer of the same architecture, built fresh by the caller, whose parameters are overwritten with the model’s on construction. Passing the model itself, a layer sharing a parameter object with it, or one on another device or dtype is a contract violation; a model moved with to needs its average moved the same way. Two parameters over one storage, which the contract cannot see, average to themselves: the copy and the update read both tensors before writing either. Buffers are neither copied nor averaged, as PyTorch’s AveragedModel leaves them by default; the average keeps the buffers it was built with. A diffusion model sampled from its averaged weights rather than its latest ones gives markedly cleaner images, the reason DDPM training keeps one; the default decay is that paper’s.

procedure

(ema-update! e) → void?

  e : ema?
Moves every averaged parameter to decay times itself plus (- 1 decay) times the model’s, under with-no-grad. The first update copies instead of averaging, as PyTorch’s AveragedModel does, so an average built before training tracks the trained weights rather than the initial draw.

procedure

(ema-average e) → layer?

  e : ema?
The averaged layer, the one to evaluate with.

procedure

(ema-decay e) → (real-in 0 1)

  e : ema?
The decay e was built with.

procedure

(ema? v) → boolean?

  v : any/c
Whether v is an average built by ema.
